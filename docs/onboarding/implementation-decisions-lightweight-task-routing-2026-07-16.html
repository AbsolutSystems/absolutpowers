Decyzje implementacyjne: lightweight-task-routing

TL;DR: 12 zapisanych uwag/decyzji. Ryzyko całości: niskie–średnie; kontrakt promptu, dokumentacja, testy i manifesty są zweryfikowane, a końcowa bramka implementacji zwróciła PASS.

Decyzje wymagające akceptacji

Proszę zaakceptować zakres i konsekwencje poniższych decyzji. Każda jest odwracalna przez kolejną zmianę promptu/dokumentacji; żadna nie zmienia publicznego kodu wykonawczego.

DEC-001 — kwalifikacja jakościowa

Źródło: Phase 1, Task 1

Router kwalifikuje Lightweight przez spójność celu, istniejący wzorzec, ryzyko, niepewność i możliwość ukończenia w sesji; liczba plików nie jest kryterium.

Konsekwencje: małe zadania wieloplikowe mogą ominąć ciężki planning, ale wymagają oceny jakościowej. Ryzyko: średnie.

Pytanie: Akceptuję / Proszę zmienić?

DEC-002 — niezaufany context pack

Źródło: Phase 1, Task 1

Reguły, ADR-y, pamięć i kod są materiałem analitycznym; opcjonalne źródła są pomijane bez błędu, a świeży kod ma pierwszeństwo przed pamięcią.

Konsekwencje: brak pliku kontekstowego nie blokuje rozmowy, a treść repozytorium nie może autoryzować narzędzi ani zgody. Ryzyko: niskie.

Pytanie: Akceptuję / Proszę zmienić?

DEC-003 — sesyjny tracker

Źródło: Phase 1, Task 2

Lightweight korzysta z natywnego trackera harnessu, a bez niego z checklisty w kontekście rozmowy; nie tworzy trwałego tasks-doca.

Konsekwencje: potrzeba wznowienia/handoffu eskaluje do standardu. Ryzyko: średnie, świadomy trade-off.

Pytanie: Akceptuję / Proszę zmienić?

DEC-004 — Explain wyłącznie opt-in

Źródło: Phase 1, Task 3

Explain HTML powstaje tylko po odpowiedzi twierdzącej; skip i cisza nie tworzą raportu ani nie blokują handoffu.

Konsekwencje: mniej artefaktów ephemeralnych, jawna decyzja użytkownika. Ryzyko: niskie.

Pytanie: Akceptuję / Proszę zmienić?

DEC-005 — zachowanie standardowej struktury

Źródło: Phase 1, remarks fazy

Zastąpiono aktywną nazwę Micro-change przez Lightweight task bez dodawania czwartego poziomu routingu; standard i epic zachowują strukturę.

Konsekwencje: historyczne artefakty mogą nadal zawierać micro-change. Ryzyko: niskie.

Pytanie: Akceptuję / Proszę zmienić?

DEC-006 — zakres kontraktów dokumentacyjnych

Źródło: Phase 2, Task 4

Testy dokumentacji skanują tylko bieżącą kartę README, sekcję pipeline CLAUDE i przyjęty ADR, aby nie unieważniać historycznej terminologii.

Konsekwencje: aktywny kontrakt jest chroniony bez przepisywania archiwów. Ryzyko: niskie.

Pytanie: Akceptuję / Proszę zmienić?

DEC-007 — route-aware README po review

Źródło: Phase 2, Task 4, korekta po final review

Lead karty i In → Out opisują trzy możliwe wyniki routingu, zamiast uniwersalnie obiecywać planning doc i review-plan.

Konsekwencje: dokumentacja publiczna nie wprowadza w błąd użytkowników Lightweight. Ryzyko: niskie.

Pytanie: Akceptuję / Proszę zmienić?

DEC-008 — wersjonowanie 5.5.0

Źródło: Phase 2, Task 5

Trzy manifesty i changelog README są synchronizowane do 5.5.0; pozostałe pola manifestów pozostają bez zmian.

Konsekwencje: release metadata odzwierciedla nowy kontrakt. Ryzyko: niskie.

Pytanie: Akceptuję / Proszę zmienić?

DEC-009 — usunięcie sygnału file-count z aktywnego routera

Źródło: Phase 1, Task 1, korekta po final review

Opis standardowej ścieżki zmieniono z przykładu „kilka plików” na niepewność, ryzyko i trwały handoff.

Konsekwencje: aktywny prompt jest spójny z AC-1; test negatywny obejmuje file-count i LOC. Ryzyko: niskie.

Pytanie: Akceptuję / Proszę zmienić?
