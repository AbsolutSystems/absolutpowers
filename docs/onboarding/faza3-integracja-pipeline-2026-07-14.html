1. TL;DR

To mały meta-feature na samym repo AbsolutPowers (skille to pliki markdown/prompt — brak runtime'u i build systemu; wszystkie AC są grep/strukturalne). Sedno: do 4 skilli pipeline (feature-discuss, generate-tasks, implement, review) dodajemy ujednolicony blok prozą ## Terminal state deklarujący, co dany skill dostarcza i jaki jest następny krok w łańcuchu.

Cel: model prowadzony przez /goal Claude Code („Set a goal Claude checks before stopping") nie może zatrzymać się przedwcześnie w środku pipeline'u (np. uznać robotę za skończoną po generate-tasks). Blok jawnie mówi „pipeline niedomknięty aż do skilla terminalnego (review/triada-review/ship)". Świadomie bez formatu maszynowego — /goal czyta prozę, nie parser (YAGNI).

Dodatkowo 3 mniejsze poprawki wychwycone w review: (1) udokumentowanie „Execution Handoff" jako N/A (jeden egzekutor: implement sterowany polem Mode, nie fork obry subagent-driven-vs-executing-plans); (2) dodanie brakującego filtra Status: active przy odczycie project-memory do agents/implementation-worker.md — realna naprawa latentnego buga; (3) cleanup martwego labelu „gnhf" (strip w archiwach + relabel w żywym feature-discuss).

2. Pytania i decyzje dla człowieka

Najcenniejsza sekcja — tu potrzebny jest człowiek. 5 pozycji.

Q1 — Zakres grepa AC-9 kontra istniejący plik onboarding zweryfikowane

AC-9 wymaga, by grep -rl "gnhf" … docs/ zwracał pusto. Ale w repo już istnieje docs/onboarding/faza1-feature-discuss-brainstorming-2026-07-13.html, który zawiera 3 wystąpienia „gnhf". Plan nie wymienia tego pliku na liście do sprzątnięcia. Bez jego wyczyszczenia AC-9 nie przejdzie. Decyzja: czyścimy też ten HTML, zawężamy grep AC-9, czy uznajemy artefakt onboardingowy za wyjęty spod reguły?

Q2 — Ten raport też zawiera token „gnhf" zweryfikowane

Ironia meta-feature'u: ten plik (docs/onboarding/faza3-…html) omawia cleanup gnhf, więc sam zawiera token „gnhf" i leży w docs/ — czyli w zasięgu grepa AC-9. Jeśli AC-9 sprawdza się po wygenerowaniu tego raportu, wynik nie będzie pusty. Powiązane z Q1 — ta sama decyzja o zakresie grepa (rozdzielić „shipowany prompt" od „dokumentacji człowieka" wygląda na najzdrowsze wyjście).

Q3 — Czy ship dostaje blok terminal-state? wnioskowane

Otwarte pytanie z planu. review jest gate'em (fix-loop / merge), nie ostatnim ogniwem — realnym punktem „dowieziony feature" bywa merge/PR przez ship. ship nie był w pierwotnej czwórce. Wstępnie: tak, ale do potwierdzenia — inaczej łańcuch pod /goal może się urwać na review zamiast na merge.

Q4 — Faza 4 planu migracji: rescope czy wyciąć? wnioskowane

gnhf jest nieużywany, a Faza 4 planu migracji jest o „gnhf/headless". AC-10 wymaga tylko notki przy Fazie 4, że wymaga rescope'u. Ostateczna decyzja (rescope vs całkowite wycięcie) jest świadomie poza tym featurem — trzeba ją podjąć osobno.

Q5 — „Docs sweep" jest warunkowy zweryfikowane

Krok 5 planu i pliki CLAUDE.md/README.md są oznaczone „jeśli potrzeba". Żaden AC (AC-1..AC-13) nie wymusza edycji CLAUDE.md/README. Decyzja: czy opis pipeline w CLAUDE.md ma wspomnieć o kontrakcie terminal-state, czy zostawiamy dokumentację bez zmian? Ryzyko cichego pominięcia.

Wzorzec bloku (proza, adaptowany per skill)

## Terminal state
Stan terminalny tego skilla: <co jest dostarczone>.
Następny krok w pipeline: `@<next-skill>` (<warunek/kiedy>).
Pipeline NIE jest domknięty na tym etapie — jeśli działasz pod `/goal`,
kontynuuj do skilla terminalnego (`@review`/`@triada-review` lub ship/merge),
zanim uznasz cel za osiągnięty.

6. Wybrane rozwiązania i uzasadnienie

Proza, nie format maszynowy

Jedyny realny konsument to /goal — model czyta prozę, nie parser. gnhf (który motywował format maszynowy w planie migracji) jest nieużywany. Format maszynowy (next: we frontmatterze) = spekulacja pod nieistniejący parser → YAGNI. Rezerwa: gdyby pojawił się headless parser, dodać wtedy pod jego faktyczny format. AC-11

Ujednolicenie, nie dodanie warstwy

Handoffy już istnieją luźno; wartość jest w spójności + jawnym „pipeline niedomknięty", nie w nowej mechanice. Stąd wymóg zastąpienia starych linii, nie dublowania. AC-7

Execution Handoff jako decyzja/doc, nie kod

Fork obry (subagent-driven vs executing-plans) zakładał dwóch egzekutorów. AbsolutPowers ma jednego: implement, sterowanego Mode. To analog, nie brakująca funkcja — więc go tylko dokumentujemy. AC-5

Filtr project-memory jako realna naprawa

To nie kosmetyka: worker jako jedyny komponent pipeline czytał project-memory bez filtra i mógł użyć wpisów superseded/archived jako aktywnych podpowiedzi. Brzmienie trzymamy spójne z implement/SKILL.md (jedno źródło konwencji). AC-12

7. Ryzyka i otwarte kwestie

wysokie — AC-9 vs docs/ (grep zbyt szeroki). Istniejący onboarding Fazy 1 i ten raport zawierają token „gnhf" w docs/, który AC-9 obejmuje. Bez zawężenia grepa lub wyczyszczenia tych plików AC-9 nie przejdzie. zweryfikowane (patrz Q1/Q2)
średnie — Duplikacja handoffu. Trzeba zastąpić istniejące „Następny krok" (feature-discuss l.355/406, generate-tasks l.647), nie dodać obok — ryzyko dwóch sprzecznych deklaracji następnego kroku. Wymaga przejrzenia każdego pliku przed wstawieniem. AC-7
średnie — Relabel zamieniony w strip (regresja companiona). W feature-discuss logika fallback (brak Node, tryb nieinteraktywny) MUSI zostać — usuwamy tylko słowo „gnhf". Przypadkowy strip logiki = regresja ścieżki headless/Codex/Pi. AC-9b
średnie — Cross-platform drift. CLAUDE.md nakazuje edytować pary Claude/Codex razem (m.in. generate-tasks, implement). Plan operuje ścieżkami skills/ i agents/ bez prefiksu claude//codex/ — do potwierdzenia, czy zmiany terminal-state trafiają też do drzewa codex/. wnioskowane
niskie — review to gate, nie ogniwo. Jego terminal-state musi opisywać domknięcie/fix-loop/merge, a nie udawać „→ następny skill". Nisko, bo jawnie zaadresowane w planie. AC-6
niskie — Kolejność harvest vs review w implement. Blok terminal-state implement musi objąć istniejący nudge do harvest spójnie (harvest opcjonalny przed commitem, review to gate), nie tworzyć drugiego, sprzecznego zalecenia. AC-8

9. Glosariusz

  • terminal-state — jawna, prozą pisana deklaracja na końcu skilla: co dostarczono i jaki następny krok. Kontrakt czytany przez model, nie parser.
  • /goal — feature Claude Code („Set a goal Claude checks before stopping"): model sprawdza przed zatrzymaniem, czy cel osiągnięty. Realny konsument bloku terminal-state.
  • Execution Handoff — pojęcie z obry (dwa tryby egzekucji). W AbsolutPowers N/A: jeden egzekutor implement + pole Mode (orchestrated/single-file).
  • project-memory / Status: active — project-memory.md gromadzi „pułapki"; tylko wpisy Status: active są aktywnymi podpowiedziami (superseded/archived ignorowane).
  • gnhf — nieużywane narzędzie z planu migracji (motywowało format maszynowy). Do usunięcia jako martwe założenie; w żywym prompcie relabel na „headless".
