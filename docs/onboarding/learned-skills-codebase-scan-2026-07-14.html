1. TL;DR

Plan odwraca źródło sygnału uczenia się skilla try-learn-skill: zamiast destylować procedurę z artefaktów jednego zakończonego feature'a (planning + tasks + git diff, generalizacja z n=1), skill ma skanować cały codebase i wyciągać procedury powtarzalne — kwalifikuje się wzorzec występujący w kodzie ≥3 razy (z dowodem file:line), a użytkownik zatwierdza kandydatów zbiorczo (batch approval).

Przy okazji znika mechanika ledgera kandydatów i „promocji przy drugim wystąpieniu" (niepotrzebna, gdy skan widzi wszystkie wystąpienia naraz) oraz cały skill harvest — jego jedyna unikalna funkcja (archiwizacja artefaktów feature'a) przenosi się do skilla ship. Pipeline traci nudge do harvestu na rzecz nudge'a do ship.

weryfikacja To zmiana wyłącznie w plikach promptów (SKILL.md) i dokumentacji — brak runtime'u i build systemu, więc każde AC jest sprawdzalne grepem/strukturalnie. Zweryfikowałem bezpośrednio, że stan wyjściowy zgadza się z opisem planu (patrz tabela poniżej).

2. Pytania i decyzje dla człowieka

4 kwestie do rozstrzygnięcia przed implementacją. Dwie pierwsze są w planie oznaczone jako „Pytania otwarte" z wstępną odpowiedzią — warto je potwierdzić.

  1. Próg N=3 — stały czy parametryzowany? Plan proponuje stałą domyślną 3 z możliwością podania innej wartości w argumencie (np. --min=N). AC-2 wymaga jawnie liczby 3 jako domyślnej. Decyzja: zostawiamy stałą 3 + wzmianka o override, czy pełny flag?
  2. Migracja istniejących learned-skilli / _candidates.md w target-projektach — plan stawia to poza scope. Czy na pewno? Projekty, które już uzbierały wpisy w starym formacie, zostaną z osieroconym _candidates.md, którego nowy skill nie czyta.
  3. wnioskowane Sposób przenoszenia plików w archiwizacji (git mv vs mv) — plan mówi „rozważ zgodnie z tym jak harvest przenosił pliki", ale nie rozstrzyga. To wpływa na rozszerzenie allowed-tools w ship: git mv mieści się w istniejącym Bash(git:*), ale mv wymagałoby dodania Bash(mv:*). Warto ustalić jedną drogę.
  4. Zakres domyślnego skanu przy dużym repo. Plan zakłada „domyślnie cały codebase" + opcjonalny scope-arg jako hamulec kosztu. Czy przy naprawdę dużym repo domyślny pełny skan jest akceptowalny, czy skill ma raczej wymuszać zawężenie? (ryzyko kosztu, patrz sekcja Ryzyka)

Granica vs update-ai-context (wymagana sekcja w nowym skillu)

Plan podkreśla, że nowy try-learn-skill musi jawnie odgraniczyć się od update-ai-context, bo oba skanują codebase:

  • update-ai-context → pasywna dokumentacja: patterns.md / rules.md / CLAUDE.md — „tak wygląda ten projekt", czytane biernie jako tło dla AI.
  • try-learn-skill → aktywne, wywoływalne procedury: „tak SIĘ ROBI powtarzalną procedurę X" — learned-skille, które agent odpala. Inny cel, inny artefakt.

5. Wybrane rozwiązania i uzasadnienie

  • Codebase-scan zamiast feature-artefaktu. Powtarzalność w całym kodzie jest twardym, weryfikowalnym sygnałem reużywalności; pojedynczy diff to zgadywanie z n=1. Zmiana źródła rozwiązuje problem u korzenia zamiast łagodzić go ledgerem.
  • Usunięcie ledgera po zmianie źródła. Ledger istniał tylko po to, by łapać „2. wystąpienie" między izolowanymi sesjami feature'ów. Skan widzi wszystkie wystąpienia naraz, więc mechanizm staje się zbędny — nie jest to utrata funkcji, tylko usunięcie protezy.
  • Usunięcie harvest = mniej maszynerii. Wrapper bez wartości: document-feature i document-module są już samodzielnymi commandami, a try-learn wychodzi na zewnątrz. Jedyna unikalna funkcja (archiwizacja) dostaje naturalny dom w ship. Odrzucono osobny mikro-command archive-feature (kolejny command do pamiętania) oraz zostawienie harvestu jako orkiestratora (pusta skorupa).
  • Batch approval zamiast gate-per-skill. „Procedura" jest z natury fuzzy — próg ≥N zawęża maszynowo, człowiek tnie ostatecznie. Batch jest szybszy przy bootstrapie wielu skilli naraz i daje tę samą kontrolę co gate per skill.

Odrzucone alternatywy (z planu): zostawić try-learn na artefaktach i tylko podkręcić próg (nie adresuje korzenia — n=1 zostaje n=1); zostawić harvest jako orkiestrator; archiwizacja jako osobny command; human gate per-skill jako domyślny (wolne przy bootstrapie).

6. Ryzyka i otwarte kwestie

Wysokie — Osierocona archiwizacja. Jeśli przeniesienie logiki KROK 4 do ship jest niepełne (skrót zamiast pełnej logiki + gate + hard boundary), artefakty feature'ów przestają być sprzątane, a stary punkt ich sprzątania (harvest) już nie istnieje. Task musi przenieść PEŁNĄ logikę, nie jej streszczenie.
Wysokie — Uprawnienia ship pod tool-gatingiem Claude'a. zweryfikowane Obecny allowed-tools to Read, Glob, Grep, Bash(git:*), Bash(gh auth:*), Bash(gh pr:*) — brak Write i mkdir. Bez rozszerzenia frontmattera krok archiwizacji cicho nie zadziała (brak uprawnień do utworzenia katalogu i zapisu summary.md).
Średnie — Założenie „harvest już zarchiwizował" w ship. Trzeba je usunąć/odwrócić, inaczej ship będzie szukał archiwum, którego nikt już nie tworzy przed nim (AC-9). Wymaga reconcile sekcji odczytu artefaktów.
Średnie — „Procedura" jest fuzzy — szum / false-positive. Skan może produkować wzorce bez realnej proceduralności (sama duplikacja kodu ≠ procedura). Próg ≥N + batch + wymóg dowodu file:line to filtry; skill musi jawnie odrzucać nie-procedury i przy braku kandydatów kończyć bez zapisu (AC-8).
Średnie — Kolizja z granicą update-ai-context. Bez jawnej sekcji demarkacji feature odtworzy niejasność „dwa narzędzia skanujące codebase". Sekcja granicy jest wymagana (AC-7), nie opcjonalna.
Niskie — Koszt skanu dużego repo. Opcjonalny scope-arg + próg ograniczają koszt; skill powinien pozwolić zawęzić zakres (patrz pytanie #4).
Niskie — Rewizjonizm w archiwaliach/docs. Grep czyszczący odwołania do harvest musi celować TYLKO w żywe prompty (skills/, agents/, CLAUDE.md, README.md). Archiwalne dokumenty (absolutpowers/archives/, docs/onboarding/*.html, changelog w README) są POZA grepem — ich edycja byłaby rewizjonizmem (AC-10).

8. Glosariusz

  • learned-skill — wygenerowany, wywoływalny SKILL.md zapisany w target-projekcie pod .claude/skills/learned/{name}/, kodujący powtarzalną procedurę tego projektu.
  • candidate-ledger (_candidates.md) — dotychczasowy plik-notatnik gromadzący obserwacje kandydatów na skille między sesjami; usuwany w tym feature.
  • batch approval — jednoprzebiegowe zatwierdzanie: skan pokazuje całą listę kandydatów naraz, użytkownik zaznacza które zapisać, zapis obejmuje wyłącznie zaznaczone.
  • harvest phase — dotychczasowy „closeout" po implement: orkiestrator uruchamiający try-learn → document-feature → document-module → archiwizacja. Usuwany w całości.
  • tool-gating / allowed-tools — mechanizm Claude Code, w którym skill deklaruje we frontmatterze dozwolone narzędzia; niezadeklarowane narzędzie jest zablokowane w runtime.

weryfikacja Zweryfikowano bezpośrednio w repo: istnienie skills/harvest/SKILL.md, aktualne allowed-tools skilla ship, feature-artefaktowy tryb + ledger w obecnym try-learn-skill.
